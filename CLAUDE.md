# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Kubernetes operator (kubebuilder / controller-runtime, Go) that watches RSS/Atom feeds
described by `FeedGroup` custom resources and posts new entries to Discord via incoming
webhooks. Single API group, single kind: `FeedGroup` (`rss2discord.maverickd650.dev/v1alpha1`).

`AGENTS.md` is the detailed companion guide — it covers kubebuilder/CLI scaffolding workflows,
API/controller marker conventions, and the project's hardening rationale in depth. Read it
when scaffolding new APIs/webhooks or touching the security-sensitive paths below.

## Commands

Tasks are defined in `.mise/config.toml` and run via `mise run <task>`. **This is the single
source of truth — CI installs the pinned tool versions with `mise` and runs the same tasks, so
local == CI.** Do not invoke `go test`/`golangci-lint` directly; use the tasks (they wire up
codegen, envtest assets, and the custom lint binary).

- `mise run test` — unit tests (runs `manifests`, `generate`, `fmt`, `vet` first; uses envtest = real K8s API server + etcd; `-race -coverprofile cover.out`). Excludes `/e2e`.
- `mise run test-e2e` — e2e tests against a throwaway Kind cluster (created/deleted automatically; never run against a real cluster).
- `mise run lint` / `lint-fix` — golangci-lint. Note: this project builds a **custom** golangci-lint binary (`.custom-gcl.yml` adds the `logcheck` module plugin), so the `lint` task depends on `golangci-lint-custom` which produces `bin/golangci-lint-custom`.
- `mise run build` — build manager binary to `bin/manager`.
- `mise run run` — run the controller locally against the current kubeconfig context.
- `mise run manifests` — regenerate CRDs + RBAC from `+kubebuilder` markers.
- `mise run generate` — regenerate `zz_generated.deepcopy.go` and the server-side-apply types in `api/v1alpha1/applyconfiguration/`.
- `mise run helm-chart-refresh` — regenerate `dist/chart/` from `config/` (kubebuilder's `helm/v2-alpha` plugin), preserving this chart's hand-tuned templates. Run after CRD/RBAC/manager changes; see AGENTS.md for what it preserves and why.

Run a single test (after `mise run manifests generate` so codegen is current):
```bash
go test ./internal/controller/ -run TestName -v          # one Go test
go test ./internal/controller/ -run TestX -args -ginkgo.focus="substring"   # focus a Ginkgo spec (suite_test.go uses Ginkgo+Gomega)
```

After editing `*_types.go` or markers, run `mise run manifests generate`. After editing any
`*.go`, run `mise run lint-fix` and `mise run test`.

## Architecture

The reconcile loop is: for each `FeedGroup`, fetch every feed → filter → template/render →
send to Discord → record per-feed delivery state in `FeedGroup.Status`. Three internal packages:

- `internal/rss` (`client.go` fetch, `transport.go` SSRF-guarded HTTP client, `parse.go`/`rss.go`/`atom.go` parsing, `identity.go` entry identity, `previous_identity.go` the `PreviousID` shim) — fetches and parses feeds. Conditional GET via ETag/Last-Modified, response-size cap. An Atom document's vocabulary is decided once from its root namespace: in Atom 1.0 the identity/link/date elements are matched by namespace (`atomEntry`) so extension `<ext:id>`/`<ext:link>` can't displace them; other documents are read by local name (`looseAtomEntry`). When this changes an entry's ID versus earlier releases the parser reports it as `Entry.PreviousID` (`withPreviousIDs`, `previous_identity.go`: it re-reads the document by local name, but only when an Atom entry has a direct `id`/`link`/`updated`/`published` child outside Atom's namespace, `mayReadIdentityDifferently`), and the controller (`migrateIdentities`) carries stored identities over.
- `internal/discord` (`client.go`) — builds and sends webhook messages. `SendMessage` is `prepareRequest` (pure: validation, `Fit`, URL parse, HTTPS + `AllowedWebhookHosts` check, thread query, payload marshal -- no network, no limiter, so a rejected host never reaches either) then `(*Client).exchange` (limiter wait/reserve, HTTP call, status mapping, `notePacing`); `redactURLError` is the one place a `*url.Error` is stripped, so no error from either step contains the webhook URL/token. Rate-limit/error handling, `@everyone`/`@here` suppression via `allowed_mentions`, length limits (all of Discord's limits live in `discord.Fit`, `fit.go` -- per-field caps, the 6000 combined embed clamp and thread name; `feedRenderer.build` calls it once and `SendMessage` re-applies it idempotently; `renderTemplate` output is raw). Non-http(s) link/image stripping (`javascript:`/`data:`) lives in `internal/controller/sanitize.go` (`httpURLOrEmpty`), not here.
- `internal/msgtemplate` (`msgtemplate.go`, `funcs.go`) — the message-template sandbox: `Compile` -> opaque `*Template` -> `Execute`. Rejects `range`/`define`/`template`/`with`, variable assignment and string-building builtins (`printf`, `html`, ...); caps output size and `replace` results. It is the only production package that may import `text/template` (`TestOnlyTheSandboxImportsTextTemplate`, `callers_test.go`, fails otherwise), so a template can't be parsed without the checks or run without the cap. The controller keeps the entry mapping (`templateData`, `renderTemplate`).
- `internal/controller` — entry presentation is sanitized once, into a `displayEntry` (`display.go`, `displayOf`), which both the embed (`feedRenderer.build`) and the templates (`templateData`) read; the sanitizers themselves (`stripHTML`, `httpURLOrEmpty`) are in `sanitize.go`. `FeedGroupReconciler` (`feedgroup_controller.go`) orchestrates everything, plus `feed_sync.go` (a `feedSync` applies one fetch to a `FeedStatus`: it owns the order of the steps and the single settlement point), `attempt.go` (a `feedAttempt` owns outcome → metric/condition/Event/retry), `metrics.go` (Prometheus) and `classify.go` (error → outcome classification).

Cross-cutting designs that span multiple files (change these carefully):

- **The per-feed path depends on two ports, not concrete clients.** `ports.go` defines `FeedFetcher` (satisfied by `*rss.Client`) and `MessageSender` (satisfied by `*discord.Client`), used by the reconciler's `RSSClient`/`DiscordClientBuilder` and by `processFeed`/`entryDelivery`. `processFeed(ctx, feedRun)` is a plain function over one `feedRun` value (group, feed, `fetched fetchOutcome`, `sender`, the reconcile's `cadence`, an optional `events.EventRecorder` -- nil drops Events -- and `now`); it does not need the reconciler, so tests build a `feedRun` with `testRun(t, ...)` (`testrun_test.go`), which also drops the group's metric series when the test ends. `Reconcile` (the Kubernetes I/O) reads as `prepareStatus` (`ensureFeedStatuses`, backoff reset on a spec change, the status snapshot, the pruned URLs whose metrics it forgets) → webhook (`webhook`: lookup, trim, empty-is-error, `noteWebhookSecretVersion`) → `clientsFor` (wraps the ports in `timedFetcher`/`timedSender`; nil ports were defaulted once per reconciler by `withDefaults`, from `SetupWithManager` or the first reconcile, with one shared HTTP client and `discord.RateLimiter`) → `reconcilePass` (the pure middle, driven in `reconcile_pass_test.go` with the port fakes: `planFeeds` → `fetchAll`, concurrent, ordered `[]fetchOutcome`, status only read until it returns → `processFeed` fold, which stops after a Discord rate limit) → `settleGroup` (`settle.go`: ObservedGeneration, `summarizeGroup`, the InvalidInterval Event, gauges, no-op-write skip, `applyStatus`) → requeue. Status code is split by module: `status_store.go` (clamping, `ensureFeedStatuses`, `feedStatusFor`, `setFeedCondition`, the SSA write), `group_summary.go` (Ready/FeedReachable) and `settle.go`; condition and Event reasons that aren't failure classes live in `conditions.go` (the classes stay in `classify.go`) -- every reason string in production code is a const, and their values are user-visible API (`TestProductionReasonsAreNamedConstants`, `reasons_test.go`, fails if a string literal reaches a `Reason`/`conditionReason` field or a reason argument of `setFeedCondition`/`setCondition`/`warn`/`Eventf` -- traced back through local and package variables, the package's helpers' results and, by making them sinks too, functions' parameters -- or a reason-named variable or helper). The timing adapters are the only place `feedRequestDuration` is observed — a test calling `processFeed` directly that asserts that histogram must wrap its client with `newTimedSender`. In-memory fakes of the ports (`ports_test.go`) can script 429/5xx/4xx without HTTP; mock-server tests stay on the real clients, which exercise the real error mapping.

- **SSRF guards — do not weaken or duplicate.** RSS URLs and the webhook secret are user-supplied. `internal/rss/transport.go`'s `newDefaultHTTPClient` uses a custom `DialContext` that resolves the host and rejects any non-public IP (loopback, link-local, private, unspecified, multicast, CGNAT) via `isPublicIP`. `internal/discord/client.go` only sends to HTTPS hosts in `AllowedWebhookHosts` (Discord domains). Tests that need to hit local `httptest` servers use the unguarded `testRSSClient()` in `internal/controller/*_test.go` (or `srv.Client()` of an in-memory `httptest.NewTestServer`); mock Discord servers sit on that in-memory network and are addressed as real `https://discord.com/...` webhook URLs, so they pass the production allowlist unchanged and no test writes to `discord.AllowedWebhookHosts`. Tests of the guards themselves stay on real loopback (the in-memory client bypasses the dialer) — never relax the production guards for tests. `TestProductionCallersKeepTheSSRFGuard` (`internal/rss/callers_test.go`) parses every production file and fails if a caller passes `rss.NewClient` anything but `nil`, uses `NewClientWithTransportWrap` outside `cmd/`, or builds an `http.Client`/`http.Transport` or uses `http.DefaultClient`/`DefaultTransport`/`http.Get` outside `transport.go` and `discord/client.go`. (A `security-reviewer` subagent guards these two files.)

- **A fetch is applied by a `feedSync`, and settled in exactly one place.** `processFeed` only opens one (`openFeedSync`) and calls `(*feedSync).apply(ctx, run, attempt)`, which runs the whole sequence — record the fetch outcome (`feedAttempt.record`), `withoutEntries`, the render-config check, `begin`, the capped-legacy log line, the backlog-skip record, `entryDelivery.run` — derives the `syncVerdict` from how far it got and calls `close` exactly once as its last act (not deferred, so a panic mid-sequence leaves the status unsettled; `close` panics only on a non-verdict). `begin` owns the order: stamp title → stable sort → delivery ledger (`ledger.go`, built once over the sorted, *untrimmed* fetch: the single identity index: one `identityRecord` per entry plus every uniqueness count, computed once at construction, which alone owns the `LastSent` key scheme, the `LastSeenEntry` writes and the stripped-key ownership questions `carriesOver`/`ownsPrevious`; the legacy pass hands it recovered identities and never builds a key -- `forgetIdentity`, `recordSentAt`, `entryKeySent`, and `identitySent` for its pre-ledger read) → identity migrations (`migrateIdentities`, `identity_migration.go`: the one entry point, legacy then previous-identity, writing only through the ledger's methods (index-based, so they can't write an arbitrary identity); they change the status, never the entries, so the ledger's counts hold across them; everything specific to a pre-`stateVersion`-1 status -- `legacyState`, `migrateLegacyIdentities`, the ambiguous catch-up cap, the `StateVersion` advance -- lives in `legacy.go` (its pre-ledger `readLegacyState` is the one read of the status without a ledger), which `feedSync` and `planDelivery` reach only through `blocksInitialize`, `capCatchUp`, `logLegacyCatchUpCap` and `settleOnClose` and which never builds a `LastSent` key itself, so dropping legacy support is deleting that file and those calls) → watermark lookup (`watermarkLookup`: none/found/lost) → `planDelivery` (catch-up limit, backlog skip; `delivery_plan.go` is the catch-up module: `catchUpLimitOf` is the only reader of `Spec.CatchUpLimit`, and with `defaultCatchUpLimit` and `limitCatchUp` it lives there; `feedSync` stores the `deliveryPlan`). The send loop reads the sync only through `entries`, `sent`, `markHandled` and `renderEvidence`, which delegate to `deliveryPlan.entries`/`renderEvidence` (the render-failure skip's evidence window: the plan's whole scan, untrimmed past-watermark entries included, catch-up-trimmed ones not). `close` is the only code that sets `Initialized`, the legacy `StateVersion`, persists ETag/Last-Modified, clears `LastError`/`RetryCount`/`BackoffUntil` and prunes `LastSent`. Don't settle anywhere else, and don't call `begin` before the config check: a config error must leave the status untouched. Terms are in `GLOSSARY.md`.
- **Per-feed status is a slice, not maps.** `FeedGroup.Status.Feeds []FeedStatus` (keyed by `rssUrl`); each struct holds `LastChecked`/`LastSeenEntry`/`LastSent`/`LastError`/`ETag`/`LastModified`/`RetryCount`/`Conditions` together. `ensureFeedStatuses` rebuilds the slice every reconcile (in `Spec.Feeds` order), initializing new feeds and pruning removed ones in one pass; `feedStatusFor` looks one up by URL. New per-feed state goes on `FeedStatus`, not a new parallel map.

- **Status is written with server-side apply.** `applyStatus` converts `FeedGroup.Status` to the generated `api/v1alpha1/applyconfiguration` types and calls `Status().Apply` as field owner `feedgroup-controller`. After changing `FeedGroupStatus`/`FeedStatus`, run `mise run generate` — `TestStatusApplyConfigurationCoversEveryField` fails if the apply configuration is stale (a missing field would otherwise be silently dropped from every status write).

- **Metrics use a single outcome label.** Every fetch/send attempt increments `feedOperationsTotal` (only in `feedAttempt.record`, via `attemptOutcome.metricLabel`) with exactly one `outcome` (`outcomeSent`, `outcomeFetchError`, `outcomeSendError`, `outcomeRenderError`, `outcomeRateLimited`). `fetch_error`/`send_error` are sub-classified by cause in `classify.go` (e.g. `fetch_error_not_found`) — `outcomeFetchError`/`outcomeSendError` are only ever label *prefixes*, never recorded raw. The Grafana dashboard (`dist/chart/dashboards/feedgroup-overview.json`) and PrometheusRule alerts match these with anchored regexes, so a new outcome usually needs a dashboard panel/alert too.

- **Failure classification → status conditions.** `classify.go` maps an error to a `failureClass`: a Prometheus-safe `metricReason`, a CamelCase `conditionReason` (e.g. `HTTP404`), and a `permanent` flag. `classifyFetchError` matches only `internal/rss`'s typed errors (`ParseError` -- which wraps every parse failure, including the `UnrecognizedFormatError` checked ahead of it -- `ResponseTooLargeError`, `InvalidURLError`), never `encoding/xml` types. `conditionReason` becomes the `Reason` on a feed's `Reachable` (fetch) or `Delivered` (render/send) condition; the group-level `FeedReachable` condition summarizes the most common failure — so `kubectl get feedgroup -o yaml` explains *why* a feed is down. Persistent-failure Events fire exactly once — for a transient failure when `RetryCount` first reaches the retry limit (`==`, not `>=`), for a permanent fetch/send failure (which backs off immediately) when its backoff first hits the cap — so an ongoing failure doesn't re-fire every reconcile. That retry policy is written once, in `feedAttempt.record` (`attempt.go`), which every fetch/render/send/skip/config outcome goes through as `record(outcome, err)` and which derives the `failureClass` from the outcome kind and the error itself (callers never classify; a `*discord.RateLimitError` from a send is resolved to the rate-limited outcome there); it returns an `attemptVerdict` (`retry`, `retryAfter`, `pending`) that `Reconcile` folds across feeds and `processFeed` turns into the `feedSync` close verdict (`pending` → `syncPending`). Don't increment the metric, set `Reachable`/`Delivered`, touch `LastError` or emit these Events anywhere else; `RetryCount` and `BackoffUntil` belong to `retryRun` (next bullet), which `record` drives.

- **`retryRun` (`backoff.go`) owns a feed's retry run: `RetryCount`, `BackoffUntil` and the phase.** `runOf(fs)` is a view over a `FeedStatus`; it is the only production code that reads or writes those two fields (comments aside) and the only place that encodes the phase rule (fetch run = `Reachable` False, delivery run = `Reachable` True; the phase is inferred, never stored, so `fetchSucceeded` and `fail(phaseFetch)` must run before `record` sets `Reachable` -- the type doc explains). Operations: `fetchSucceeded()` (ends a fetch-phase run only), `fail(phase)` (starts a new run if the in-progress one is the other phase, then `RetryCount++`), `belowLimit`/`exhaustedNow`/`pastLimit(max)` (the retry-limit comparisons: `<`, `==`, `>`), `outstanding()` (`RetryCount > 0`), `active(now)`, `extend(base, now) (firstCapped)` with the backoff math (`permanentBackoffDuration`, the 6h `maxPermanentBackoff` cap and its overflow guard), `clear()` (zeroes both, re-arming `firstCapped`) and `sendCaused()` (backed off by a send failure, inferred from `Reachable` not being False). `feedAttempt` keeps the metric, condition, Event, verdict and `LastError`: `feedAttempt.backOff` emits the once-only `BackoffCapped` Event when `extend` reports `firstCapped`; `clearFailure`, `clearPermanentBackoffs` (spec change) and `clearSendBackoffs` (webhook Secret version change, `secret_watch.go`) call `clear`; `planFeeds` calls `active`. `feedCheck` (`check.go`, `checkOf(fs)`) is the matching view of a feed's last check: `failed` (LastError set: Ready's count and the `feed_healthy` gauge), `failedOrRetrying` (also `outstanding()`: the scheduler's "always due", deliberately wider), `lastChecked` and `untilDue` (the one parse of LastChecked, shared by `feedDue`, `planFeeds`' nextDue and the last-checked gauge). Scheduling (`planFeeds`, `feedPlan.requeue`, `requeueDecision`, `feedDue`) lives in `schedule.go`; the timing it and `feedAttempt` run on (poll interval, retry interval/backoff base, retry limit, floors, fallbacks and the invalid-duration error the Ready condition reports) is resolved once from the spec by `cadenceOf` (`cadence.go`) -- nothing else parses `Spec.Interval`/`RetryInterval`/`Retries`.

- **`dist/chart/` has hand-tuned files `mise run helm-chart-refresh` knows to preserve.** `templates/manager/manager.yaml`, `templates/metrics/controller-manager-metrics-service.yaml`, and `templates/prometheus/controller-manager-metrics-monitor.yaml` carry shortened resource-name suffixes and (the ServiceMonitor) the native-histogram `scrapeProtocols`/`scrapeNativeHistograms` block; `templates/rbac/manager-role.yaml` and `manager-rolebinding.yaml` render a Role/RoleBinding per `rbac.watchNamespaces` entry (with `manager.yaml` passing the same `--watch-namespaces`, plus `--watch-webhook-secrets` and a chart-only list/watch Secrets rule when namespace-scoped or `rbac.clusterWideSecretWatch` is set), so after changing `+kubebuilder:rbac` markers copy the new rules from `config/rbac/role.yaml` into `manager-role.yaml` by hand (`TestChartManagerRoleRulesMatchConfig` fails until you do); `values.yaml` and `templates/_helpers.tpl` carry the `prometheusRule`/`grafanaDashboard`/`prometheus.scrapeNativeHistograms` values and the `controllerManagerName` helper; `templates/prometheus/grafana-dashboard.yaml`, `templates/prometheus/prometheus-rule.yaml`, and `dashboards/*.json` are wholly custom (no kubebuilder equivalent). Hand-editing `dist/chart/` directly is fine, but don't follow it with a raw `kubebuilder edit --plugins=helm/v2-alpha --force` — that regenerates `values.yaml`/`_helpers.tpl` from scratch and discards those edits. Use `mise run helm-chart-refresh` instead.

## Do not edit (auto-generated)

`config/crd/bases/*.yaml`, `config/rbac/role.yaml`, `**/zz_generated.*.go`, `api/*/applyconfiguration/**` (from `mise run manifests`/`generate`), and `PROJECT` (kubebuilder). Never delete `// +kubebuilder:scaffold:*` markers. Use `kubebuilder create api`/`create webhook` to scaffold — don't hand-create those files. Edit `config/samples/*` (example CRs) freely.

## Never write bare cross-repo issue/PR references

Don't write `owner/repo#123` (e.g. `kubernetes-sigs/kubebuilder#4809`) anywhere that becomes a commit
message, PR title/body, or comment in this repo — not even when citing an upstream issue as
background/rationale. GitHub auto-links that exact syntax and creates a "mentioned this issue"
notification on the *other* repo, pinging its maintainers about something they have no connection
to and didn't consent to. This isn't hypothetical: it happened once already (a PR description cited
an upstream kubebuilder issue this way, got squash-merged into `main`, and had to be scrubbed via a
history rewrite — see PR for this fix).

If you need to cite an external issue/PR, write it so GitHub won't autolink it: use the full URL
(`https://github.com/owner/repo/issues/123`) or break the pattern (`owner/repo issue 123`), never the
bare `owner/repo#123` shorthand.
